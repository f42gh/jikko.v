# Jikko 全体師匠本

## 0. この文書の役割

この文書は、`/Users/f42/dev/jikko.v` 全体を読むときの総合案内です。

狙いは次の 3 つです。

1. いまのコードベースを、ただのファイル群ではなく `意図を持った生き物` として理解すること
2. `本当に作りたい Jikko` と `いま存在する Jikko` の差分を明確にすること
3. 今後の改修や再設計で、守るべき核と壊してよい殻を見分けられるようになること

## 1. まず結論

いまの Jikko は、`今やるべきことを 1 件に絞り、着手と完了を助ける` という核において、思想はかなり明確です。

その核は主に次の 3 文書に刻まれています。

- `../BRIDGE.md`
- `../DESIGN.md`
- `../TECH_STACK.md`

そしてコードの中心は次の 4 点です。

- `../src/domain/tasks/*`
- `../src/domain/scoring/*`
- `../src/app/proto-state.ts`
- `../src/app/App.svelte`

ここだけは、何度でも読み返す価値があります。

逆に言うと、Jikko を理解するときに、いきなり `Tauri` や `Drizzle` から入るのは順番が逆です。

## 2. この repo の正しい見方

この repo は、`完成された綺麗な層構造` として読むより、`強いドメイン仮説を持ったプロトタイプが、徐々に構造化されつつある状態` として読むべきです。

これは欠点ではありません。

むしろ大事なのは、未整理な箇所を見つけたときに、すぐに「汚い」と断じることではなく、

- どの混乱が本質的な混乱か
- どの混乱が移行途中ゆえの仮の混乱か
- どの混乱が中核ループを壊しているか

を見分けることです。

## 3. Jikko の核

Jikko の核は、`タスク管理` ではありません。

Jikko の核は、次の問いへの実装上の返答です。

`人は、やるべきことがあるのに、なぜ着手できないのか。どうすれば、今やるべきことを迷わず始められるのか。`

ここから、プロダクトの約束が生まれています。

- 今やるべきことを 1 件だけ前に出す
- なぜそれが今なのかを説明する
- 着手の摩擦を下げる
- 完了を自信と長期 ROI に変換する

したがって、Jikko を改修するときの問いはいつも同じです。

`この変更は、ユーザが今の 1 件に着手しやすくなるか。`

## 3.5 設計の気持ち

この repo に流れている気持ちは、`全部入りの正しさ` ではありません。

むしろ次です。

- まず中核ループを守る
- そのために必要なだけ構造を持つ
- 過度な抽象化は後回しにする
- それでも未来に整理できる seam は残す

つまり Jikko は、見栄えのよいアーキテクチャ図より、`今やるべき 1 件へ届くこと` を先に選んでいます。

## 6. どこが真実か

この repo では、`どこを真実とみなすか` を間違えると急に苦しくなります。

基本原則は次です。

1. プロダクト意味の真実は `BRIDGE.md` と `DESIGN.md`
2. ドメイン構造の真実は `src/domain/tasks/types.ts`
3. 優先順位ロジックの真実は `src/domain/scoring/engine.ts`
4. セッション中の状態遷移の真実は `src/app/proto-state.ts`
5. 永続化の現実は `src/infra/db/schema.ts` と `src-tauri/src/main.rs`

ここで重要なのは、`永続化の現実` と `ドメインの真実` は同じではない、という点です。

たとえば `Task` の domain 型はかなり絞られていますが、DB スキーマには旧モデルの列が残っています。

これは「DB が真実ではない」ということです。

むしろ今は、

- domain が未来の姿
- DB は過去との互換を抱えた現実

と理解する方が自然です。

## 9. 実装の現在地

### 9.1 強い点

- OODA の状態設計が明確
- スコアリングが決定論的
- ローカルファーストの前提がぶれていない
- UI が中核ループに集中している
- ドメインとインフラを分けようという意志がある

### 9.2 過渡期の点

- `App.svelte` がまだ大きい
- `proto-state.ts` が application service / store / boot orchestration を兼ねている
- DB スキーマに旧属性が残っている
- イベント型には現行 UI で未使用の概念が残っている
- Tauri 側の schema 初期化も旧列を引きずる

### 9.3 注意すべき誤読

見た目だけで `クリーンアーキテクチャ未完成だからダメ` と判断してはいけません。

本当に問うべきなのは、

- 中核ループが表現できているか
- 判断ロジックが透明か
- 将来の分離に耐える seam があるか

です。

いまの Jikko は、少なくともその種は持っています。

### 9.4 改善余地

- 文書上で強い思想を、コード上の明示的な不変条件へさらに寄せられる
- `proto-state.ts` に集まった責務は、安定した境界から順に分けられる
- 永続化の互換事情は、将来の migration 方針としてもう一段文書化できる

## 10. これから育てるときの原則

### 10.1 まず守る

何かを大きく変える前に、まず次の不変条件を守ります。

- `observe` はランキング対象外
- `orient` だけが評価対象
- `act` は同時に 1 件だけ
- `done` は `act` を経由する
- 優先順位は説明可能で再現可能
- AI に最終判断を委ねない

### 10.2 次に整理する

いきなり抽象化しすぎず、まず seam を明確にします。

例:

- `proto-state.ts` から boot orchestration を切り出す
- ranking / recommendation の境界を明確にする
- repository の record mapper を整理する
- DB の旧列を段階的に廃止する

### 10.3 最後に洗練する

構造が見えてから、はじめて DDD やクリーンアーキテクチャの型に寄せます。

逆です。

先に型に寄せてはいけません。先に意味を守ります。

## 11. この repo を参考に、自分で Jikko を創るとはどういうことか

それは、このコードをそのまま模写することではありません。

本当にやるべきなのは次です。

1. この repo が守ろうとしている約束を見抜く
2. その約束を実現する最小構成を自分の頭で再構築する
3. いまの repo の良い部分だけを持ち帰る
4. 余分な過渡期構造は、そのまま持ち帰らない

つまり、`コードの再利用` より `判断基準の継承` が大事です。
