# スコアリングと説明可能性

## 1. Jikko の価値は、推薦そのものではなく推薦の納得感にある

Jikko は `おすすめ機能` を持つアプリではありません。

Jikko は、`なぜ今それをやるのかを、自分で理解できる形で返す` アプリです。

だから、スコアリングで大事なのは精度だけではありません。

もっと大事なのは次です。

- 再現可能であること
- 説明できること
- 入力が理解可能であること
- 調整可能であること

## 2. 現行実装

中心は `../src/domain/scoring/engine.ts` です。

主な計算は次の通りです。

```ts
roi = (task.roiScore ?? 1) * weights.roi
effortPenalty = max(1, estimatedMinutes / 25) * weights.effortPenalty
priorityScore = roi - effortPenalty
expectedRoi = roi / max(effortPenalty, 0.5)
```

この式の良いところは、簡単なことです。

簡単であることは、未熟さではありません。

少なくとも v1 では、簡単で説明できる式は武器です。

## 2.5 設計の気持ち

ここにある気持ちは、`完璧に当てること` ではありません。

むしろ、

- 何を見て決めたかが分かる
- 外したときに直せる
- ユーザ自身が判断の癖を学べる

ことを優先しています。

Jikko において recommendation は、支配ではなく補助です。

## 3. なぜブラックボックスにしないのか

`DESIGN.md` にもある通り、AI に中核判断を委ねない、という方針があります。

これは技術制約ではなく、プロダクト哲学です。

理由は明確です。

- ユーザが自分の判断を学べなくなる
- 推薦を信頼できなくなる
- 誤りの原因を点検できなくなる
- 調整可能性が落ちる

Jikko は `自分の頭を奪うアプリ` ではなく、`自分の判断を支えるアプリ` であるべきです。

## 4. roiScore と estimatedMinutes は何か

これらは単なるフォーム入力ではありません。

### roiScore

- 主観的な価値評価
- 今やる意味の大きさ
- 将来リターンの期待

### estimatedMinutes

- 着手コスト
- 認知負荷
- 今日の文脈で抱えられる重さ

つまり Jikko は、`価値` と `摩擦` のバランスを見ています。

これは本質的に良い設計です。

人は重要なことをやれないのではありません。

多くの場合、`価値は高いが摩擦も高い` ために止まります。

## 5. whyNowSummary の意味

`whyNowSummary` はいま単純ですが、将来とても重要になります。

現状は、

`ROI x.x / Cost x.x`

という要約です。

しかし本質は、スコアの内訳を文字列にすることではありません。

本質は、`この推薦は何を見てこうなったのか` を人間に返せるようにすることです。

将来改善するなら、説明は次の 3 層に分けるとよいです。

1. 一言の理由
2. 数値の内訳
3. 比較理由

例:

- 一言: `短く終わるわりに見返りが大きい`
- 内訳: `ROI 4, 25分, penalty 1.0`
- 比較: `他候補より開始コストが低い`

## 6. rankTasks と selectNextTask を分ける意味

スコアリングと最終選定が分かれているのは、今後の拡張に効きます。

たとえば、

- 単純スコアは高いが、直前に timeout したので今日は避ける
- 同点なら分割済みタスクを優先する
- 連続して長時間タスクが続くのを防ぐ

といった選定戦略は `planning` に逃がせます。

この分離は、小さくてもかなり大切です。

## 7. analysis はスコアの改善ループである

`../src/domain/analysis/metrics.ts` と `../src/domain/analysis/suggestions.ts` は、単なる後付けダッシュボードではありません。

ここでやっているのは、実績から次の判断の癖を点検することです。

例:

- timeoutRate が高い
- averageRoiGap がマイナス
- reorientationRate が高い

これらはすべて、`次の recommendation を少し賢くする材料` です。

つまり analysis は、ドメインの外側にある飾りではなく、`判断精度の内省装置` です。

## 8. よりよいスコアリングとは何か

よりよいスコアリングは、単に特徴量を増やしたスコアリングではありません。

本当に良いのは次です。

- 入力負担が増えない
- 理由が伝わる
- 失敗しても修正できる
- 局所最適ではなく、着手しやすさを上げる

この観点でいうと、`説明できない精密さ` は多くの場合、悪化です。

## 9. 将来加えるなら何を加えるか

もしスコアリングを拡張するなら、私は次の順番を勧めます。

1. timeout 履歴による軽微なペナルティ
2. reorientation 率による不確実性補正
3. decomposition 済みかどうか
4. 連続重タスク回避の flow 補正

逆に、最初から複雑な多因子モデルを入れるのは危険です。

なぜなら、学ぶべきものが増えすぎて、Jikko の透明性が死ぬからです。

## 9.5 ありがちな誤読 / 誤実装

- 特徴量を増やせば賢くなると思ってしまう
  - 説明不能な複雑さは、Jikko では価値より害が大きいことがあります。
- AI に最終スコアを決めさせたくなる
  - recommendation の納得感と学習可能性が落ちます。
- `whyNowSummary` を飾りテキストだとみなす
  - 実はここは、将来の説明責務の核です。

## 9.6 改善余地

- `whyNowSummary` を比較理由まで含む表現へ育てる余地がある
- `selectNextTask` は将来の flow 制御の受け皿になれる
- analysis 指標を使った軽微な補正は、透明性を保ったまま追加できる可能性がある

## 10. 説明可能性は UX である

これは大事なので強く言います。

説明可能性は、機械学習の倫理用語ではありません。

Jikko において説明可能性は UX です。

なぜなら、

- 納得できると始めやすい
- 理由が分かると修正しやすい
- 自分の判断の癖を学べる

からです。

`なぜ今これか` に答えられないなら、その推薦は UI に出すべきではありません。

## 11. 師匠としての一言

スコア式をいじるとき、数式を賢くしようとしすぎてはいけません。

先に問うべきは次です。

`この変更で、ユーザは前より納得して着手できるか。`

もし答えが曖昧なら、その変更はまだ早いです。

## 12. 鍛錬課題

### 課題 1

`../src/domain/scoring/engine.ts` を読んで、現行の `priorityScore` が高くなる条件を自然言語で説明してください。

### 課題 2

候補タスクを 2 つ自分で仮定し、`roiScore` と `estimatedMinutes` を入れて、どちらが上位になるかを手計算してください。

### 課題 3

`whyNowSummary` を将来改善するとしたら、`一言の理由 / 数値の内訳 / 比較理由` の 3 層で各 1 例ずつ書いてください。
