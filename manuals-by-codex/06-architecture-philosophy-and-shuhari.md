# 設計哲学、DDD、クリーンアーキテクチャ、守破離

## 1. まず最初に

DDD やクリーンアーキテクチャは、採点基準ではありません。

あれは `よりよいソフトウェアを作るための思考補助具` です。

これを忘れると、人はすぐに次の罠に落ちます。

- 用語を使えることを理解だと勘違いする
- 層を増やすことを設計だと勘違いする
- 抽象化の数を品質だと勘違いする

Jikko を育てるなら、絶対にそこへ行ってはいけません。

## 2. DDD を Jikko に翻訳する

DDD の本質は、複雑さを `業務の意味` に沿って整理することです。

Jikko に翻訳すると、まず次が大切です。

### 2.1 ユビキタス言語

Jikko にはもう言葉があります。

- observe
- orient
- act
- done
- roiScore
- estimatedMinutes
- recommendation
- act_timed_out

これらはただのラベルではありません。

この言葉をぶらさないことが、最初の DDD です。

実際には、その言葉は次のようなファイルに埋め込まれています。

- `../src/domain/tasks/types.ts`
- `../src/domain/scoring/engine.ts`
- `../src/app/proto-state.ts`

### 2.2 ドメインの中心

Jikko の中心は `Task` と `Task の状態遷移` です。

もしここを見失って、

- UI コンポーネント構造
- DB テーブル都合
- ライブラリの作法

が設計を支配し始めたら、ドメインは負けています。

### 2.3 境界づけられた文脈

大げさな言い方をする必要はありませんが、Jikko の中には少なくとも次の文脈があります。

- task lifecycle
- scoring / recommendation
- history / analysis
- persistence

今は 1 人用のローカル app なので、無理に巨大な bounded context 分割をする必要はありません。

でも、文脈の違いを意識するだけで、責務の混線はかなり減ります。

## 3. クリーンアーキテクチャを Jikko に翻訳する

クリーンアーキテクチャの本質は、`重要なものを外側の都合から守る` ことです。

Jikko における `重要なもの` は何でしょうか。

私はこう答えます。

- OODA の状態遷移
- recommendation の判断原理
- ユーザの認知負荷を下げるという約束

これらが中心です。

だから外側に置くべきものは次です。

- Svelte
- Tauri
- SQLite
- Python helper

現実のコードでも、この方向性はかなり見えています。

たとえば、

- `../src/domain/tasks/types.ts`
  - 中心に近い
- `../src/app/proto-state.ts`
  - application 的責務を暫定的に抱えている
- `../src/infra/db/repositories/tasks-repository.ts`
  - 外界との接続を引き受ける adapter

という読み方ができます。

## 4. いまの repo は clean か

完全ではありません。

でも、`clean ではないから価値がない` という評価は浅いです。

いまの repo には次があります。

- domain 層の独立性
- infra adapter の意識
- UI と domain を分けようとする意志

足りないのは、application layer の明示と、過渡期データ構造の整理です。

つまり、`思想は clean に向いているが、まだ途中` です。

## 4.5 設計の気持ち

この repo で学ぶべきなのは、パターンの正誤表ではありません。

むしろ、

- 何を中心に置くか
- 何を外側へ追いやるか
- 何をまだ抽象化しないか

という、設計の引き算です。

Jikko は、まだ途中だからこそ、その引き算の跡が見えます。

## 5. よりよいソフトウェアとは何か

よくある誤解があります。

よりよいソフトウェアとは、

- ファイル数が多いこと
- 抽象クラスがあること
- ディレクトリが綺麗なこと

ではありません。

本当に大事なのは次です。

### 5.1 意味が壊れにくい

小さな変更でドメインの約束が崩れないこと。

### 5.2 読んだときに意図が追える

なぜこの構造なのかを、未来の自分が説明できること。

### 5.3 誤りが局所化する

ミスしたときに、被害範囲が読めること。

### 5.4 進化の余地がある

今は未完成でも、次の一手を打ちやすいこと。

Jikko は、まさにこの `進化の余地` を持った repo です。

## 6. 守破離

あなたがこの repo を土台に本当に自分の Jikko を作るなら、守破離はとても大事です。

### 守

まず守る段階では、勝手に賢くならないことです。

守るべきは次です。

- OODA の状態設計
- 1 件に絞るという約束
- 説明可能な recommendation
- 中核判断を AI に渡さないこと
- observe で判断を要求しないこと

この段階では、既存コードの構造よりも `既存思想の不変条件` を守ります。

### 破

次に破る段階では、いまの実装の弱さを見極めて壊します。

壊してよいものの例:

- proto-state の責務過多
- App.svelte の一部肥大化
- DB schema の旧多因子列
- まだ使い切れていない event 種別

ただし、壊すときにも核は壊しません。

`observe は observe のまま`
`act は 1 件のまま`
`推薦は説明可能なまま`

これが条件です。

### 離

最後の離では、もはやこの repo の形に縛られません。

あなた自身が、

- どこまで domain を濃くするか
- application layer をどう切るか
- analysis をどこまで中核に入れるか
- UI をどこまで定規的にするか

を、自分の言葉で決められる状態です。

この段階ではじめて、本当に自分の Jikko になります。

## 7. 師匠として勧める学び方

### 7.1 まずコードを書く

自然言語で理想を言えないなら、先に小さく実装するのが正しいです。

### 7.2 次に名前をつける

書いたものに対して、

- これは何を守っているのか
- 何を犠牲にしているのか
- なぜこの形なのか

を言語化します。

### 7.3 それから哲学に戻る

その後で DDD や clean architecture を読むと、初めて血肉になります。

逆順だと、言葉だけが増えます。

## 8. Jikko における悪い抽象化

避けたいのは次です。

- 実体のない service 名
- まだ安定していない責務の無理な分離
- domain の都合ではなくフレームワーク都合の命名
- 未来のためと言いながら現在を読みにくくする抽象化

抽象化は、未来への保険である前に、現在への負債にもなります。

## 9. Jikko における良い抽象化

良いのは次です。

- OODA の状態境界
- scoring と planning の分離
- domain と persistence の変換境界
- runtime 差分を repository へ閉じ込めること

これらは、意味に沿った分離です。

## 9.5 ありがちな誤読 / 誤実装

- DDD を用語集だと思ってしまう
  - 大事なのは言葉の輸入ではなく、意味の統一です。
- clean architecture を層の数だと思ってしまう
  - 守るべき中心が曖昧なまま層だけ増やすと、むしろ悪化します。
- 守破離の `破` だけ先にやりたくなる
  - 何を守るか曖昧なまま壊すと、ただの解体になります。

## 9.6 改善余地

- Jikko 独自のユビキタス言語を、今後さらに文書化できる
- application layer を明示すると、clean architecture 的な説明はもっとしやすくなる
- ただし整理の順序を誤ると、思想より抽象化が前に出る危険がある

## 10. 最後の教え

あなたが目指すべきなのは、DDD をできる人でも、clean architecture を語れる人でもありません。

目指すべきは、

`自分が守りたい体験のために、どの複雑さを受け入れ、どの複雑さを拒否するかを決められる人`

です。

それが設計者です。

そして Jikko のようなプロダクトでは、その力こそが一番大事です。
