# 中核ループとドメイン

## 1. ここを理解しない限り、Jikko は理解できない

Jikko の本体は UI ではありません。DB でもありません。

本体は `中核ループ` です。

`observe -> orient -> decide -> act -> done`

ただし重要なのは、`decide` は永続状態ではなく、`orient` 済みタスクのランキング処理である、という点です。

この考え方は `../BRIDGE.md` と `../DESIGN.md` に明記され、実装では主に次に現れています。

- `../src/domain/tasks/types.ts`
- `../src/domain/tasks/factory.ts`
- `../src/domain/scoring/engine.ts`
- `../src/domain/planning/select-next.ts`
- `../src/app/proto-state.ts`

## 2. OODA はただの比喩ではない

Jikko における OODA は、雰囲気づけの言葉ではなく、状態機械の規律です。

### observe

- 入力の置き場
- まだ判断を要求しない
- `title` と最小限のメモだけでよい
- ランキング対象ではない

observe の本質は、`考える前に置けること` です。

ここで多くを要求すると、Jikko はただの重い Todo になります。

### orient

- タスクに意味を与える段階
- `roiScore` と `estimatedMinutes` を決める
- `orientMemo` で補助軸を残せる
- 初めてランキング対象に入る

orient の本質は、`やるべきことを判断可能な形にすること` です。

### decide

- 永続 status ではない
- `orient` の集合に対してスコアを計算し、今やるべき 1 件を選ぶ処理

これは非常に良い判断です。

なぜなら、`decide` を状態にしてしまうと、画面都合で状態が増え、ドメインより UI が強くなるからです。

### act

- 実行中
- `actStartedAt` と `actDueAt` を持つ
- 同時に 1 件だけ

Jikko が `今やるべき 1 件` を本当に守るなら、act が複数存在してはいけません。

### done

- 完了
- ただし `act` を経由したものだけが到達する

ここも重要です。

`done` を雑に許すと、Jikko は `考えた気になって終わるアプリ` になります。

## 3. domain/tasks/types.ts をどう読むか

`../src/domain/tasks/types.ts` は、いまの Jikko が何を Task と呼ぶかの定義です。

ここには少なくとも次の思想が含まれています。

- Task は最小の行為単位である
- 状態は OODA を反映する
- ROI と時間見積もりは task に属する
- 実行痕跡も task に残す

この型は、今後どれだけ UI を作り直しても、かなり長く残る可能性があります。

だからここを読むときは、`現在の画面に必要な項目` としてではなく、`Jikko が世界をどう切り取るか` として読んでください。

## 4. factory.ts をどう読むか

`../src/domain/tasks/factory.ts` の `createObservedTask` は小さいですが、とても重要です。

なぜなら、ここで新規タスクが必ず `observe` から始まることを保証しているからです。

これは単なる初期値設定ではありません。

`入力は、まず置く。すぐ判断させない。`

というプロダクト哲学の埋め込みです。

## 5. scoring と planning は何を分担しているか

`../src/domain/scoring/engine.ts` は、各 task を評価します。

- scoreTask
- rankTasks

一方で `../src/domain/planning/select-next.ts` は、ランキング済みの候補から最終 1 件を選びます。

現状は単純に先頭を返すだけですが、この分離には意味があります。

- scoring は `候補の評価`
- planning は `最終選定`

将来、

- 同点時の扱い
- act 履歴を踏まえた補正
- 今日の流れや疲労を踏まえた選定

などを追加したくなったとき、この境界が効きます。

## 5.5 設計の気持ち

ここにある気持ちは、とても素朴です。

`人は、考える箱と、実行する箱が混ざると止まる。`

だから Jikko は、

- まず置く
- 次に意味づける
- それから決める
- 決めたら 1 件だけやる

という順番を、状態そのもので守ろうとしています。

この順番を守るために OODA があり、Task 型があり、TaskEvent が存在しています。

## 6. DDD 的に見るなら何が中心か

Jikko に DDD を当てるなら、まず大事なのは用語を外から持ってくることではありません。

まず、この repo がすでに持っている `ユビキタス言語` を見つけます。

### すでにあるユビキタス言語

- observe
- orient
- act
- done
- roiScore
- estimatedMinutes
- recommendation
- timeout
- reoriented

これは立派なドメイン言語です。

DDD の第一歩は、英語らしい抽象名を増やすことではなく、この言葉たちの意味をチーム内でぶらさないことです。

## 7. Task は aggregate root か

現時点では、かなりそのように扱われています。

- Task が中心
- TaskEvent は Task にひもづく履歴
- 完了や再評価は Task の状態変化として記録される

ただし、実装上は `Task` と `TaskEvent` の一貫性を repository の操作で保っているだけで、明示的な aggregate として厳格に閉じているわけではありません。

それでも、概念上の中心が Task であることは明確です。

## 8. event は何のためにあるか

`TaskEvent` は履歴のためだけではありません。

本質的には、

- どんな判断が行われたか
- なぜ再見積もりが必要になったか
- 完了はどんな条件で起きたか

を、後から分析可能にするための痕跡です。

Jikko において履歴は decoration ではありません。

履歴は `次の判断の材料` です。

## 9. act timeout を失敗にしない思想

`act_timed_out` を単なる失敗として扱わず、`orient に戻す入口` としているのはとても良い設計です。

ここには、良いソフトウェアの大事な態度があります。

それは、ユーザを裁かないことです。

時間切れは、

- 見積もりが大きすぎたのかもしれない
- 分割が甘かったのかもしれない
- 今日は文脈が悪かったのかもしれない

という再観察の材料です。

Jikko はここで、`失敗ログ` ではなく `学習ループ` を作ろうとしています。

## 10. ここから先に育てるなら

ドメインを強くするなら、次の順で考えるとよいです。

1. 状態遷移の不変条件をもっと明示する
2. TaskEvent の意味を整理する
3. decomposition を正式なドメイン操作として入れるか判断する
4. recommendation に説明責務を持たせる
5. 完了後の reward / reflection を本当に中核に入れるか決める

## 10.5 ありがちな誤読 / 誤実装

- `decide` を永続 status に増やしたくなる
  - 画面の都合で状態を増やすと、ドメインが UI に引っ張られます。
- `done` をどこからでも付けられるようにしたくなる
  - 完了の意味が薄れ、中核ループの緊張感が消えます。
- observe で最初から多くの入力を求めたくなる
  - 入力摩擦が増え、Jikko が重い管理アプリへ戻ります。

## 10.6 改善余地

- `Task` の状態遷移を関数としてより明示的に閉じる余地がある
- `TaskEvent` の種類と利用箇所を整理して、現役イベントと将来イベントを分けられる
- decomposition を本当にドメインへ昇格させるなら、仕様と言葉を先に固める必要がある

## 11. 師匠としての一言

DDD を学ぶと、つい entity や aggregate という言葉を先に使いたくなります。

でも、いちばん先に身につけるべきなのは次です。

`このアプリでは、何が起きたと言えるのか。何が起きたとは言えないのか。`

Jikko なら、

- observe に置いただけでは、まだ判断していない
- orient しただけでは、まだ実行していない
- act を通って初めて、done に意味が出る

この区別を守り抜くことが、ドメインを守るということです。
