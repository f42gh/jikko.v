# jikko UI デザイン学習ノート

## 目的

この文書は、`jikko` の UI を自分で設計できるようになるための実践ノートです。

狙いは次です。

- 良し悪しを感覚ではなく言葉で判断できるようにする
- いまの `jikko` に必要な画面の強さを見抜けるようにする
- Codex に頼らず、自分でラフを切って改善できるようにする

これは一般論だけのデザイン論ではありません。

`jikko` のような `認知負荷を減らし、今やるべきことを 1 つ示すプロダクト` を前提にしています。

## 最初に持つべき前提

`jikko` に必要なのは、情報をたくさん見せる能力ではありません。

必要なのは次です。

- 必要なものだけ見せる
- その一瞬に必要でないものは隠す
- それでも、必要になれば迷わず取り出せる
- 1 画面の中で判断と着手が完了する

この原則を崩すと、どれだけ見た目が整っていても `jikko` らしい UI にはなりません。

## UI を判断するための 5 つの軸

画面を見たら、まず次の 5 つで採点します。

### 1. 主役が 1 秒で分かるか

最初の 1 秒で、視線がどこに行くべきかが決まっていない画面は弱いです。

`jikko` の `Now` 画面なら、主役は次の 3 つ以外であってはいけません。

- 今の対象タスク
- その判断を読むための cursor
- 行動に直結する数字

逆に主役になってはいけないものは次です。

- 補足説明
- 一覧
- 状態ラベル
- ナビゲーション
- 設定項目

### 2. 何を隠すべきかが明確か

良い UI は、何を見せるかより `何を見せないか` が明確です。

`jikko` では、常時表示しなくていいものは次です。

- 詳しい理由文
- 全スコア内訳
- 候補一覧
- 履歴の細部
- OODA の全文説明

これらは `存在してよい` が `見えっぱなしであってはいけない` です。

### 3. いま必要な操作が 1 手でできるか

`Now` 画面で必要な操作は多くありません。

- 始める
- 完了にする
- 必要なら詳細を見る

ここで別の行動を大量に置くと、画面の芯が折れます。

### 4. レイアウトが意味を持っているか

位置には意味が必要です。

`jikko` では次の意味付けが強いです。

- 中央: いまの対象
- 横方向: 時系列、比較、流れ
- 下部: 判断を支える数字と行動
- 上部: 状態やモードの最小表示

この意味が崩れると、ただの部品の並びになります。

### 5. 画面を閉じたあとでも説明できるか

良い UI は、見たあとに次のように説明できます。

`中央の窓で今の対象を読み、下の数字で価値と優先度を確認し、そのまま始める画面`

この 1 文で説明できないなら、設計がぼやけています。

## `jikko` で特に重要なデザイン態度

### 説明文で助けない

わからなさを文章で救う癖は、`jikko` と相性が悪いです。

先に考えるべき順番は次です。

1. 配置で理解できないか
2. 強弱で理解できないか
3. 数字の大きさで理解できないか
4. それでも足りないなら短文を置く

### コンポーネントではなく体験で考える

`カードを置く`
`バッジを置く`
`ナビを置く`

この発想だけで組むと、部品は増えても画面の意図は強くなりません。

まず考えるべきは次です。

- ユーザの最初の視線はどこか
- 次にどこへ流すか
- どこで判断が終わるか
- どこで行動に移るか

### 強調は 1 箇所だけに許す

緑を 3 箇所で光らせると、どこも強調ではなくなります。

`Now` 画面なら、強調は基本的に次のどちらかだけです。

- cursor
- 数字

両方を同時に強くする場合でも、片方を主、片方を従にする必要があります。

## 定規 UI をどう読むか

いま目指している reference は、`slide ruler` 的な道具の UI です。

ここで大事なのは、見た目の模倣ではなく構造の理解です。

### 定規 UI の本質

- 全体にはスケールがある
- 現在読む場所だけに窓がある
- 窓の中が主役
- 前後の情報は存在するが、薄い
- 動くのは world ではなく cursor 側に見える

これを `jikko` に翻訳すると次です。

- スケール = OODA タイムライン
- 窓 = cursor
- 窓の中 = 今の対象タスク
- 前後の薄い情報 = 過去段階と次段階
- 下にある読み値 = ROI と優先度

### いまの `Now` でさらに削れる候補

今後さらに削るなら、優先順位は次です。

1. 左右の island を常時表示しない
2. 状態ラベルをさらに記号化する
3. ナビゲーションを `Now` では細くする
4. 補助テキストを hover や detail に逃がす
5. `候補件数` や `進行中件数` を既定で隠す

## 自分でデザインするときの進め方

### ステップ 1. 画面の一言要約を書く

画面を作る前に、必ず 1 文で役割を書く。

例:

`Now は、OODA タイムライン上の現在地と、そこで実行すべき 1 件を読む画面`

これが書けないうちは、まだ作り始めない方がよいです。

### ステップ 2. 常時表示要素を 5 つ以内にする

まず紙やメモで、常時見せる要素を 5 つ以内に絞ります。

`Now` なら候補は次です。

- cursor
- タスク名
- ROI
- 優先度
- 行動ボタン

この時点で 6 個を超えるなら、何かが多いです。

### ステップ 3. hidden 要素の逃がし先を決める

隠したものは、消すのではなく逃がします。

逃がし方の候補は次です。

- hover
- click
- drawer
- detail panel
- 別画面

`隠す = 捨てる` ではありません。

### ステップ 4. モノクロで成立するかを見る

色がなくても成立するなら強いです。

確認ポイントは次です。

- 大きさだけで主役が分かるか
- 余白だけでグループが分かるか
- 線だけで構造が分かるか

### ステップ 5. 1 回で全部直そうとしない

1 回の変更で見る論点は 1 つだけにします。

よい順序は次です。

1. 情報量を減らす
2. 主役を太らせる
3. レイアウトを意味づける
4. 色を入れる
5. 装飾を最後に足す

## 実践チェックリスト

デザインを変えるたびに、次を確認します。

- 主役は 1 箇所に定まっているか
- 補助情報が主役を邪魔していないか
- 常時表示しなくてよいものが出っぱなしになっていないか
- 数字は読ませたい順番で並んでいるか
- ボタンは迷わず押せる位置にあるか
- 1 画面で完結するか
- 説明文を 1 行削っても成立するか

## Codex への依頼の仕方

自分が主導して Codex を使うなら、依頼は次の形にすると強いです。

### 悪い依頼

`なんかもっとよくして`

### 良い依頼

`主役を ROI と cursor に絞って、他は隠して`

`スクロールなしで 1 画面に収めて`

`左右の island を薄くして、中心だけ強くして`

`説明文を 2 行削っても成立する構成にして`

つまり、`完成形の気分` ではなく `何を増やし、何を消すか` で依頼するのがコツです。

## 最後に

デザインが納得いかないのは、センスがないからではありません。

たいていは次のどちらかです。

- 画面の役割がまだ言葉になっていない
- 隠すべきものを隠しきれていない

`jikko` では特に、足す力より減らす力の方が重要です。

迷ったら、まず次を自問します。

`この要素は、今この瞬間に本当に見えている必要があるか`

この問いに `はい` と言えないものは、たいてい隠してよいです。
